## Repository overview

Exif Hound is a single consolidated desktop application (no pro/community editions, no Electron). It is an npm-workspaces monorepo orchestrated by Turborepo:

- `apps/exif-hound-desktop` — the main app: Tauri 2 + React 19 + Vite + Tailwind CSS 4 + TypeScript. Leaflet for mapping, exifreader for metadata parsing, a Web Worker (`src/workers/exifWorker.ts`) for EXIF extraction, visx for analysis visualizations.
- `apps/exif-hound-website` — marketing website.
- `packages/exif-middleware` — shared EXIF middleware package (consumed by the desktop app via a Vite alias to its `dist` build; build packages before running the desktop app).

Key constraints:

- **No Electron.** The app is Tauri-only. `scripts/scan-electron.js` (root `npm run scan:electron`) exits non-zero if Electron references are reintroduced.
- **Node >= 20**, `packageManager` is pinned npm (`npm@11.x`). Use npm workspaces, not yarn/pnpm.
- Update channel is baked at build time via `EXIFHOUND_UPDATE_CHANNEL` (`stable` | `beta` | `internal`); see `apps/exif-hound-desktop/vite.config.ts` and `apps/exif-hound-desktop/turbo.json`.
- Jest/Playwright compatibility: source files must not contain `import.meta`; use the Vite `define` globals `__DEV__` and `__UPDATE_CHANNEL__` instead of `import.meta.env.*`.

## Commands

Run from the repository root (Turborepo pipelines are defined in `turbo.json`; desktop overrides in `apps/exif-hound-desktop/turbo.json`):

```bash
npm install                                   # install (also sets up Husky)
npm run dev:packages                          # build/watch shared packages
npm run tauri:dev                             # desktop app in dev mode
npm run tauri:build                           # desktop release build (current host platform only; no cross-compile)
npm run lint                                  # eslint across workspaces
npm run typecheck                             # tsc across workspaces (desktop uses tsconfig.typecheck.json)
npm test --workspace=exif-hound-desktop       # Jest unit tests (jest.config.cjs)
npm run test:e2e                              # Playwright E2E suite (desktop workspace)
npm run build:packages && npm run build:apps  # build everything
```

## Testing

### Unit tests (Jest)

- Config: `apps/exif-hound-desktop/jest.config.cjs`; setup in `src/setupTests.ts`.
- Co-located under `src/**/__tests__/`; performance-focused suites live under `src/__tests__/performance/`.

### E2E tests (Playwright)

- Config: `apps/exif-hound-desktop/playwright.config.ts`; specs in `apps/exif-hound-desktop/playwright/e2e/` (upload, exif-display, views, map, investigation, export-import, settings, theme, comparison, updater, app-shell, a11y).
- The suite serves the real UI via a dedicated Vite dev server (`npm run dev:test`, `http://127.0.0.1:5276`) — never a Tauri build. One-time setup: `npx playwright install chromium`.
- The Tauri bridge (`window.__TAURI__` / `__TAURI_IPC__` / invoked commands), reverse geocoding (Nominatim), and map tiles are mocked before app boot in `apps/exif-hound-desktop/playwright/support/app.ts` (`bootApp(page, { commands, geocoding, localStorage })`). Unknown Tauri commands reject loudly — register canned responses in `bootApp` options.
- E2E fixtures (images with known EXIF/GPS values, KML/invalid import files, tile.png) are generated by `apps/exif-hound-desktop/scripts/generate-e2e-fixtures.mjs`; expected constants are documented in `playwright/fixtures/images/README.md`. Regenerate fixtures if their constants change; do not hand-edit binary fixtures.
- Run with `npm run test:e2e` (headless, parallel) or `npm run test:e2e:ui` (interactive). Failure screenshots/traces go to gitignored output dirs (`playwright-results/`, `test-results/`).
- Viewport is 1600×900 (desktop layout); keep selectors working above the `lg` breakpoint.

### Pre-commit quality gates (Husky)

`.husky/pre-commit` runs, on every commit: desktop lint, desktop typecheck, desktop unit tests (`--runInBand`), the full Playwright E2E suite, and the desktop production build. Commits are slow by design — do not bypass the hook. If a gate fails, fix the code (or, in rare justified cases, commit with `--no-verify` and fix forward immediately).

## UI and styling conventions

- Tailwind CSS 4 via `@tailwindcss/vite`; design tokens are CSS variables in `src/index.css` under `:root` and `:root[data-theme="light"]`. Theme switching toggles `data-theme`; never hardcode colors — use the token-based utilities (e.g. `text-app-accent`, `bg-app-gray`).
- **Text selection rules**: `body` has `user-select: none` (with `-webkit-user-select` for the Electron-free Tauri WebKit/Chromium runtimes), so all non-value text (labels, headings, chrome, controls) is unselectable. EXIF/metadata **values** opt back in with the `selectable-value` class (see `ExifDetailsView.tsx`, `FullExifView.tsx`, `ImagePopup.tsx`); `input`/`textarea` remain selectable natively. When adding new UI that displays EXIF or other data values users should be able to copy, add `selectable-value`; leave labels and chrome unselectable.
- Reduced motion: `prefers-reduced-motion` makes state changes instant (see `index.css`); new animations must respect it.
- The map reticle is **off by default** (`showReticle` initial state is `false` in `src/components/Map/index.tsx`); it is toggled via map controls.

## OpenSpec feature workflow

OpenSpec is required for all new feature work in this repository. Before changing application code for a new feature, agents must:

1. Create a new OpenSpec change from the repository root, for example:

   ```bash
   openspec new change <feature-name> --description "<what is being changed>"
   ```

2. Create the proposal, requirements, design, and other applicable artifacts in that change. The feature spec must be presented to the user for approval before implementation begins.
3. After the spec is approved, use OpenSpec to create the implementation tasks from the approved spec. Do not write feature code until those tasks exist.
4. Implement the generated tasks, keeping the change artifacts up to date, and run `openspec validate --all` before declaring the feature complete.
5. Archive the completed change with OpenSpec after implementation and validation are finished.

If a feature request does not have an approved spec, stop at the specification stage and ask for approval. Bug fixes, dependency/security updates, documentation-only changes, and routine maintenance may proceed without a new feature spec unless they expand into new feature behavior.

Active OpenSpec artifacts live in `openspec/changes/` (archived changes in `openspec/changes/archive/`), and accepted capabilities in `openspec/specs/`. The E2E testing capability is specified in `openspec/specs/desktop-e2e-testing/spec.md` — note it predates the Playwright migration and still describes the original Cypress runner; follow the Playwright setup in this file and in `apps/exif-hound-desktop/README.md` for actual practice.
